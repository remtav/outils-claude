Guide du workflow des vagues

Comment passer d’une liste d’issues à une release avec le plugin Claude Code vagues : qui fait quoi, quelles règles, quels garde-fous, ce qui reste à faire à la main.

Ce guide explique et oriente. La référence d’installation, des commandes et des hooks reste le README du dépôt.

Sections

  2. Qui fait quoi
  3. Règles de planification

1. Le cycle complet

Le travail suit un chemin : des issues sont regroupées en vagues, et quelques vagues forment une release. Les commandes du plugin portent le préfixe vagues: ; c’est la seule forme documentée (/vagues:vague, pas /vague).

  1. 1. /vagues:planifier : former les vagues Lit le journal, ajuste le budget de points, redécoupe les issues bloquées, pose les étiquettes vague-N et taille-*. 
    /vagues:planifier
/vagues:planifier 3
/vagues:planifier lecture-seule
    Ce qu’on obtient : un résumé court (budget ancien → nouveau, contenu de chaque vague en points, issues redécoupées, issues en attente). Deux vagues par défaut ; un nombre en argument en forme davantage. Avec lecture-seule, tout est calculé et affiché, mais rien n’est écrit.
  2. 2. /vagues:vague N : lancer une vague Un sous-agent implémente chaque issue (trois en parallèle au plus), un autre révise chaque PR, puis la session principale fusionne ce qui est vert et approuvé. 
    /vagues:vague 3
    Ce qu’on obtient : un résumé final. 
    Vague 3 — 8/10 points
Fusionnées : #81 (issue #70), …
Ouvertes : #82 — CI absente, …
Bloquées : #71 — dépend de #70, …
  3. 3. /vagues:vague reprise : reprendre une vague coupée Pour une vague interrompue (limite d’utilisation atteinte, session fermée). 
    /vagues:vague reprise
    Ce qu’on obtient : soit Rien à reprendre (aucune vague non fermée : aucun appel GitHub, aucun sous-agent, presque aucun coût), soit la reprise là où la vague en était, l’état de chaque issue étant relu sur GitHub. Si la vague a écrit une ligne au journal il y a moins de 90 minutes, la commande s’arrête : une autre session y travaille sans doute.
  4. 4. /vagues:release : clore une release On donne le tag puis les numéros de vague. Tests complets, audit, une PR de nettoyage pour les retouches sûres, des issues pour les refactorisations lourdes, notes de version et tag. 
    /vagues:release v0.3 3 4
/vagues:release v0.1 1 2 depuis=2026-10-01
    Ce qu’on obtient : un tag annoté vX.Y sur le commit testé, mais seulement si tout est vert. Une vague qui a encore une issue ou une PR ouverte, des tests en échec ou une PR de nettoyage non fusionnée arrêtent la release sans tag. Relancer la commande reprend où elle s’était arrêtée ; un tag déjà créé donne Release <tag> déjà taguée.

Pour les détails de chaque commande, voir « Commandes » dans le README.

2. Qui fait quoi

L’orchestrateur est la session principale : il coordonne et ne code pas. Les sous-agents travaillent dans leur coin et ne lui rendent qu’une ligne, ce qui garde son contexte léger.

Orchestrateur (session principale)

modèle de ta session Exécute /vagues:vague : lance les sous-agents, lit la CI, fusionne, écrit le journal. C’est le seul à fusionner. /vagues:planifier demande le modèle claude-fable-5-2 ; /vagues:release, le modèle fable.

vagues:implementeur

Sonnet Reçoit un numéro d’issue : branche, code, tests, push, PR. Ne fusionne ni n’approuve.

#69 → https://github.com/o/r/pull/80 | réussi
#70 → — | bloqué | dépend de #69, non fusionnée

vagues:reviseur

Sonnet Reçoit une PR et son issue, vérifie les critères contre le diff, en lecture seule, et laisse un commentaire avec un marqueur de verdict lié au SHA du dernier commit.

PR #80 | approuvé
PR #81 | refusé | raison principale

vagues:release-mecanique

Sonnet Les tâches mécaniques de /vagues:release : tests, notes et tag, par le script scripts/release.py. Il ne décide rien et ne modifie aucun code.

Les agents sont lancés par les commandes ; ils ne sont pas faits pour un usage interactif.

3. Règles de planification

  • Tailles 1, 2, 4 : petite = 1 point, moyenne = 2, grosse = 4, posées en étiquettes taille-1, taille-2, taille-4. Au-delà de 4, on scinde l’issue.
  • Budget par vague : 10 points au départ ; /vagues:planifier l’ajuste (entre 4 et 20) selon les vagues coupées et l’utilisation. La somme des tailles d’une vague ne dépasse pas le budget ; une issue seule plus grosse forme sa propre vague.
  • Fichiers distincts : deux issues d’une même vague ne touchent pas les mêmes fichiers (section « Fichiers probablement touchés » du modèle d’issue).
  • Dépendances : une issue qui dépend d’une autre va dans une vague suivante.

Le journal .claude/journal-vagues.md

C’est la mémoire des vagues, dans le projet. Le budget courant (ligne budget: des réglages) n’est noté qu’à cet endroit. /vagues:vague y ajoute une ligne par événement, directement sur main, sans PR :

- 2026-11-18T14:05Z | vague 3 | ouverte | prévus 8
- 2026-11-18T14:40Z | vague 3 | issue #70 | taille 2 | fusionnée | PR #81
- 2026-11-18T16:10Z | vague 3 | fermée | complétés 8/8 | utilisation: __ %
À remplir par toi (facultatif). À la fin d’une vague, remplace le __ de utilisation: __ % par le pourcentage d’utilisation affiché dans l’app Claude. /vagues:planifier s’en sert pour ajuster le budget. Ne modifie pas les autres lignes.

4. Garde-fous

Ils sont des hooks du plugin : actifs dès que le plugin est activé, sans rien configurer. Ils s’ajoutent à ceux du projet.

Ce qui est bloquéPar quoi
Fusion et approbation par implementeur ou reviseur ; push sur main/master, push forcé, écriture MCP sur main ; le reviseur ne commite, ne pousse et n’écrit riengarde-agents-vague.py
Toute fusion de PR (même par la session principale) sans CI présente et réussie sur le dernier commit et sans verdict approuvé du réviseur pour ce même commit. Un nouveau commit invalide l’approbation. Une PR sans CI n’est donc pas fusionnée par un agentgarde-fusion.py
Fin de l’implementeur tant que la commande de vérification échoue, qu’il reste des modifications non commitées ou que sa branche est main ou non poussée (abandon après 3 blocages : réponse partiel ou bloqué)implementeur-stop-check.py

Le lint n’est pas dans le plugin : il dépend des outils de chaque projet. Dans remtav/template, par exemple, le hook lint-fichier.py du projet lance eslint sur chaque fichier .js/.mjs modifié. C’est un exemple de projet, pas une règle du plugin.

Désactiver temporairement

Variable d’environnement HOOKS_QUALITE_DESACTIVES, avec des noms séparés par des virgules : implementeur-stop-check, garde-fusion, ou tous.

HOOKS_QUALITE_DESACTIVES=garde-fusion claude
  • Dans une session cloud : variable d’environnement de l’environnement.
  • garde-agents-vague.py ne se désactive pas.
  • Un agent ne peut pas changer la variable pour lui-même en cours de session.
  • Un hook de lint propre au projet (comme lint-fichier.py dans remtav/template) peut avoir son propre nom dans la variable, selon le projet.

Voir « Hooks » dans le README.

5. Ce qui reste manuel

Le plugin ne crée rien de ceci à ta place.

Tâche planifiée de reprise

Une fois par projet, crée une tâche planifiée Claude Code (claude.ai/code, ou l’app Claude) sur le dépôt. Elle démarre une nouvelle session à chaque exécution, avec le même environnement que les sessions de vague (accès GitHub en écriture).

  • Horaire : toutes les 3 heures, par exemple 0 */3 * * * (UTC) ; 0 */2 * * * pour toutes les 2 heures.
  • Prompt :
/vagues:vague reprise

Sans vague coupée, la réponse est Rien à reprendre, presque sans coût.

Autres étapes

  • Étiquettes : /vagues:installer-vagues crée taille-1, taille-2 et taille-4 si elle a accès à GitHub ; sinon elle les liste « à créer ». Les étiquettes vague-N sont posées par /vagues:planifier.
  • Accès réseau à GitHub dans l’environnement cloud : sans lui, le marketplace ne se charge pas.
  • Après l’ajout du plugin : /reload-skills, ou une nouvelle session.
  • Protection de main : le plugin n’en suppose aucune ; le garde de fusion en tient lieu. Si ton projet en a une, c’est à toi de la régler.

Installation du plugin en session cloud

En session cloud, Claude Code n’installe pas tout seul le marketplace et le plugin déclarés dans .claude/settings.json (il n’y a pas d’invite de confiance dans ces sessions). Ce qui fonctionne : installer à la main, ou mettre ces commandes dans le script d’installation de l’environnement.
claude plugin marketplace add remtav/outils-claude
claude plugin install vagues@outils-claude --scope project
git checkout -- .claude/settings.json

Le git checkout remet .claude/settings.json tel quel : l’installation en réordonne le contenu. Pour vérifier, claude plugin list doit montrer vagues@outils-claude à l’état enabled. Par exemple, sur l’environnement de remtav/template :

if [ -d template ]; then
  (cd template && claude plugin marketplace add remtav/outils-claude && claude plugin install vagues@outils-claude --scope project; git checkout -- .claude/settings.json) || true
fi

Voir « Trois points connus des sessions cloud » dans le README.

6. Installer dans un nouveau projet

  1. 1. Copier ce bloc dans .claude/settings.json Le créer s’il n’existe pas ; sinon, fusionner ces clés avec les siennes. 
    {
  "extraKnownMarketplaces": {
    "outils-claude": {
      "source": { "source": "github", "repo": "remtav/outils-claude" },
      "autoUpdate": true
    }
  },
  "enabledPlugins": {
    "vagues@outils-claude": true
  }
}
    autoUpdate: true sert à recevoir les modifications du plugin.
  2. 2. Ouvrir une nouvelle session, puis lancer /vagues:installer-vagues Accepter le marketplace et le plugin si Claude Code le demande. La commande crée le modèle d’issue, le journal, la section « Règles de planification » de CLAUDE.md, les commandes de vérification et les étiquettes taille-*. Elle n’écrase rien et peut être relancée. Pour imposer la commande de vérification rapide : /vagues:installer-vagues "<commande>".
  3. 3. Relire et commiter, puis /vagues:planifier et /vagues:vague 1 La commande ne commite rien : tu relis les fichiers créés avant.

En session cloud, ajoute d’abord le script d’installation de la section 5. Détails : « Installer dans un projet » dans le README.

7. Dépannage

Une vague a été coupée

Lance /vagues:vague reprise (ou /vagues:vague N) : la commande marque la vague coupée, puis la reprend en relisant l’état de chaque issue sur GitHub ; les issues terminées sont sautées. Si elle répond Vague N en cours (dernière ligne …), une autre session y a écrit il y a moins de 90 minutes : attends. Pour ne plus y penser, crée la tâche planifiée de la section 5.

Une PR est restée ouverte

La raison est dans le résumé et dans le journal (ligne ouverte). Les raisons possibles :

  • CI échouée : corriger, puis relancer la vague.
  • CI absente : aucune vérification n’est configurée pour ce chemin. Le garde de fusion refuse la fusion par un agent ; fusionne la PR toi-même sur GitHub, ou désactive garde-fusion (section 4).
  • CI en attente : la commande a attendu 30 minutes au plus ; relance-la.
  • Refusée par le réviseur : la raison est dans son commentaire.
  • Refusée par le garde de fusion : la raison est donnée dans le message « Bloqué par le garde de fusion ». Il ne faut pas contourner.
  • Conflit après fusion : une autre PR de la vague a été fusionnée ; la mise à jour de la branche a échoué.
Il n’y a pas de CI

Cela arrive quand le workflow du projet ne se déclenche que sur certains chemins. Par exemple, dans remtav/template, une PR qui ne touche que .claude/ n’a aucune vérification. Le plugin ne fusionne pas sans CI, même si les tests locaux ont réussi : c’est à toi de fusionner la PR, ou de désactiver le garde.

Les commandes /vagues:… n’existent pas
  • Plugin récemment ajouté : /reload-skills, ou une nouvelle session.
  • Session cloud : l’installation automatique ne se fait pas (section 5). Vérifie avec claude plugin list ; au besoin, installe avec les deux commandes claude plugin marketplace add et claude plugin install, ou ajoute-les au script d’installation de l’environnement.
  • L’environnement doit pouvoir joindre GitHub.
Le contrôle de fin bloque l’implémenteur

Sans commande de vérification configurée, le plugin refuse plutôt que de deviner et indique où la configurer : .claude/verification-implementeur (ou la variable VERIFICATION_IMPLEMENTEUR). Même chose pour la suite complète d’une release : .claude/tests-complets (ou RELEASE_TEST_CMD).

Le plugin ne se met pas à jour

/plugin marketplace update outils-claude, puis /reload-skills ou une nouvelle session. Vérifie aussi que autoUpdate: true est dans le bloc du settings.json.

Référence : le README du dépôt remtav/outils-claude.
